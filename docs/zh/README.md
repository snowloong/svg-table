# SVG Table

本项目旨在探索如何利用 SVG、WebComponent 以及 Web Worker 技术，打造高性能、可扩展的虚拟滚动表格组件。通过自研虚拟滚动、节点池复用、分层渲染等机制，解决大数据量下表格渲染与交互的性能瓶颈，适用于对性能和可视化有较高要求的业务场景。

---

## 技术选型

| 层级/功能         | 技术选型                | 说明/理由                                 |
|------------------|------------------------|------------------------------------------|
| 组件封装         | Omi                    | 轻量、React 风格、原生支持 WebComponent  |
| 渲染层           | 原生 SVG API           | 灵活、性能好，适合可视化和动画            |
| 虚拟滚动         | 自研                   | 行列双虚拟化，适配 SVG，灵活性高          |
| 数据处理         | Web Worker（+ comlink）| 主线程不卡顿，comlink 简化通信（可选）    |
| 编辑控件         | 原生 DOM + 绝对定位    | 兼容性好，体验佳，易于实现复杂交互        |
| 动画             | 手动实现 FLIP 动画     | 细粒度控制，完全自定义，适配 SVG 场景     |
| 状态管理         | Omi 内置 reactive-signal| 简单高效，适合中小型项目                  |
| 生态/集成        | 原生/自研              | 组件可独立使用，也可集成到主流框架         |

- **渲染方式**：SVG（高度自定义、支持动画、适合可视化）
- **组件封装**：Omi（轻量、原生 WebComponent 支持）
- **高性能计算**：Web Worker（多线程，主线程不卡顿，开发门槛低）
- **性能优化**：虚拟滚动（Viewport 渲染，只渲染可见区域的行和列）
- **动画交互**：手动实现 FLIP 动画（如拖动列顺序时的平滑过渡）
- **编辑能力**：DOM 叠加实现单元格/行编辑

## 主要功能与实现思路

### 1. 大数据支持
- 支持万级甚至更大数据量，主线程只渲染可见区域，不卡顿。
- 数据的排序、过滤、分组等重计算任务交由 Web Worker 处理，主线程专注渲染和交互。

### 2. 虚拟滚动/虚拟列
- 只渲染当前视口内的行和列（如可见50行×50列），其余数据不渲染，极大减少 SVG 节点数量。
- 滚动或横向滚动时，复用 SVG 节点，动态更新内容和位置。

### 3. 动态列宽与列顺序调整
- 支持用户拖拽调整列宽，所有可见单元格的宽度和位置实时更新。
- 支持拖拽调整列顺序，采用 FLIP 动画原理实现平滑过渡。

### 4. SVG 渲染
- 每个单元格用 SVG 元素（如 `<rect>`、`<text>`）渲染。
- 表头、表体分层渲染，便于固定表头和性能优化。

### 5. 行/单元格编辑能力
- 支持单元格编辑、行编辑。
- 编辑时用 HTML DOM 元素（如 `<input>`、`<select>`、`<textarea>`）绝对定位叠加在 SVG 上方。
- 编辑完成后，将数据同步回表格数据源，并重新渲染 SVG。
- 支持键盘导航（Tab、Enter、Esc）、批量编辑、校验等高级功能。

#### 编辑流程示例
1. 用户点击单元格/行，计算该单元格/行在页面上的绝对位置。
2. 在 SVG 上方插入一个 HTML 编辑控件，并用 CSS 绝对定位到对应位置。
3. 用户编辑完成后，将新值同步到数据源，销毁编辑控件，SVG 重新渲染新内容。

## Web Worker 方案优势

- **开发门槛低**：直接用 JavaScript 编写，无需 WASM 相关知识和工具链。
- **性能足够**：对于万级数据的排序、过滤等，Web Worker 性能已能满足绝大多数业务需求。
- **主线程不卡顿**：数据处理在 Worker 线程中进行，UI 渲染流畅。
- **易于维护和调试**：Worker 代码可直接在浏览器调试，易于排查问题。

## 可行性结论

- **技术上完全可行**，SVG+虚拟滚动+Web Worker 能实现高性能和高度自定义的表格。
- **开发难度和维护成本高于 Antd Table**，但比 WASM 方案低，适合有自研能力的团队。
- **适合对性能、可视化、交互有较高要求的场景**，如金融、监控、科学计算等。
- **如只是常规业务表格，Antd Table+虚拟滚动+自定义渲染已足够，迁移意义不大。**

## 虚拟滚动原理与算法流程

### 原理
1. 只渲染可见区域：通过计算当前滚动条位置和视口大小，只渲染屏幕上能看到的那部分行和列，其余数据不渲染，极大减少渲染节点数量。
2. 动态更新可见内容：当用户滚动时，实时计算新的可见区域，复用或更新已有的渲染节点，把内容和位置切换到新的可见数据上。
3. 容器尺寸撑满：整个表格的容器高度和宽度设置为全部数据的总尺寸，这样滚动条的行为和真实大表格一致，用户体验无缝。
4. 节点复用与最小化 DOM 操作：滚动过程中，尽量复用已有的渲染节点，只做必要的内容和位置更新，避免频繁创建和销毁节点，提升性能。

### 算法流程
1. 获取滚动信息：监听滚动事件，获取当前的 scrollTop（纵向滚动距离）和 scrollLeft（横向滚动距离）。
2. 计算可见区域：根据滚动位置、视口高度/宽度、单元格尺寸，计算当前屏幕能显示的起始行/列和结束行/列的索引。
3. 确定渲染数据：只取出可见区域内的数据（如第10~30行，第2~12列），准备渲染。
4. 渲染或复用节点：用这些数据渲染对应的 SVG 元素（或复用已有节点），并设置正确的位置和内容。
5. 设置容器尺寸：整个表格的容器高度和宽度设置为全部数据的总尺寸，保证滚动条正常。
6. 滚动时重复上述流程：每次滚动时，重复1~4步，动态更新可见区域的内容和位置。

## 虚拟滚动可见区域计算算法

### 1. 固定尺寸算法
适用于所有行高、列宽都一致的场景。
- 起始行索引：startRow = Math.floor(scrollTop / rowHeight)
- 结束行索引：endRow = Math.min(totalRows, Math.ceil((scrollTop + viewportHeight) / rowHeight))
- 起始列索引：startCol = Math.floor(scrollLeft / colWidth)
- 结束列索引：endCol = Math.min(totalCols, Math.ceil((scrollLeft + viewportWidth) / colWidth))

**优点：** 计算极快，O(1) 复杂度，适合大部分表格。

### 2. 动态尺寸算法
适用于行高、列宽不固定的场景。
- 预处理：计算每一行/列的累加高度/宽度数组（前缀和数组）
- 二分查找：
  - 起始行索引：在前缀和数组中用二分查找，找到第一个大于等于 scrollTop 的索引
  - 结束行索引：找到第一个大于等于 scrollTop + viewportHeight 的索引
  - 列索引同理

**优点：** 兼容动态尺寸，滚动体验平滑，O(logN) 复杂度。

> 建议后续两种算法都实现，便于适配不同业务场景。
